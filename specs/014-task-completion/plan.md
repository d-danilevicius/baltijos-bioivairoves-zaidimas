# Implementation Plan: Task completion

**Feature:** `specs/014-task-completion/spec.md`
**Branch:** `014-task-completion`
**Status:** draft
**Depends on features:** 003-access-control, 006-confirmation-dialog, 012-student-task-list, 013-observation-card, 024-page-styling

## Summary

A student fills the answer and evidence form on the task screen (E06) and presses “Pateikti atsakymą”. A task with answer options shows the options to choose one; a task without options (a teacher task or a GBIF question from the observation card) shows a text field. The server checks the role, the class, whether the task’s group is unlocked, the answer and the evidence, and saves one submission per student and task; a second submission gives 409 and the saved answer never changes. After saving, the result screen (E07) shows the submitted answer and evidence under the label “Mokinio pateikti duomenys”. The task list shows the status “Padaryta” and “Tęsti” opens the first task that is not done. When the student leaves a form with entered data, the confirmation dialog (E21) is shown. Points, correctness, photos and repeating belong to features 015–017.

## Technical Context

- **Language and version:** C# with .NET 10 (server); TypeScript (frontend).
- **Libraries:** as selected in `docs/architecture.md` (section 1). No new library. The mapping of a submission to the response is trivial and is written as one small method; AutoMapper is not added for it.
- **Frontend:** React with Vite, React Router and Tailwind CSS. The router is changed from `BrowserRouter` to a data router (`createBrowserRouter`) only because `useBlocker` needs it (see Technical Notes).
- **Storage:** PostgreSQL through Entity Framework Core; a new table `Submissions`; migration `CreateSubmissionsTable`.
- **Testing:** xUnit (unit and integration, PostgreSQL in Testcontainers), Vitest and React Testing Library.
- **Target platform:** web application in current Chrome, Firefox, Edge and Safari; screens from 360 px width.
- **Constraints:** HTTPS only; POST uses the existing CSRF protection; no secret is stored in the repository.

## Server Request Changes

- `POST /api/my/tasks/{taskId}/submissions` – saves the answer and the evidence of the logged-in student (201 with the submission; 400 with errors per field; 401; 403 for a teacher, an administrator or a task of a locked group; 404 when the task does not exist or belongs to another class; 409 when the student has already submitted the task).
- `GET /api/my/tasks/{id}` – the response has the new property `submission`.
- `GET /api/my/tasks` – a task the student has submitted has the status `Done`; `continueTaskId` is the first task that is not done in an unlocked group.

## Data Model Changes

- New table `Submissions` (migration `CreateSubmissionsTable`): `Id`, `ClassTaskId` (empty when the task is deleted), `StudentId`, `Answer` (up to 100), `Evidence` (up to 500), `SubmittedAtUtc`; a unique index on `ClassTaskId` and `StudentId`; the foreign key to the task is `SetNull`, the foreign key to the student is cascade.

## Testing Plan

- Unit tests (`CreateSubmissionRequest`): an empty answer, an empty evidence (also only spaces), an answer over 100 characters and an evidence over 500 characters are invalid; spaces at the beginning and the end are removed before the check; a request at the limits is valid.
- Unit tests (`SubmissionService`): a valid submission is saved and returned; an answer that is not one of the options is rejected; a task without options accepts a text answer; a second submission gives `AlreadySubmitted` and the first answer stays; a task of a locked group, a task of another class, a missing task, a student without a class and a student whose membership ended give the right outcome and save nothing; a student who changed the class cannot submit a task of the old class.
- Unit tests (`StudentTaskService`): a submitted task has the status `Done`; “Tęsti” skips done tasks; when all tasks of unlocked groups are done, there is nothing to continue.
- Unit tests (`StudentTaskDetailsService`): the response has the student’s submission after submitting and has none before; the other student’s submission is not returned.
- Integration tests: a student gets 201 and the submission is in the database; the JSON has the label; a second submission gives 409 and the saved answer stays unchanged (also two requests at the same time); 400 with errors per field; a locked task gives 403 and nothing is saved; another class’s task and a missing task give 404; a task deleted by the teacher gives 404 and keeps the submissions of earlier students; the submission of a deleted task stays in the table with an empty task; a teacher gives 403; an administrator gives 403; a visitor gives 401; a request without the CSRF token is rejected; `GET /api/my/tasks` shows `Done`.
- Frontend tests: E06 shows the options or the text field by the task data; the validation messages and the counter “0 / 500”; the note “Pateikto atsakymo pakeisti nebus galima.”; submitting calls the server and shows the result with the label “Mokinio pateikti duomenys”; 400 errors are shown next to the fields; the saving failure keeps the entered data and “Bandyti dar kartą” sends again; 404 shows “Puslapis nerastas”; 403 shows “Prieiga uždrausta”; the expired session opens the login; a submitted task shows the saved answer instead of the form; the leave dialog is shown for entered data (“Išeiti” leaves, “Likti” stays) and is not shown for an empty form or after submitting; the task list shows “Padaryta”.

## Technical Notes

- The answer form follows the task data: a task with options is chosen from the options, a task without options is typed. `docs/ux.md` says “GBIF – options, teacher – text”, but the observation card question of feature 010 has no options (the answer is the number of a month), so the rule is by the options (Clarifications).
- One submission per student and task is guaranteed by the unique index, not only by a check in the service; the service turns the violation into 409, as `ClassService` does for the class code. A deleted task keeps the submission (`SetNull`) because earned points remain after a task is deleted (VT-018); the points themselves are added by feature 016, so the full check of this rule is done there.
- Whether the answer is correct is not decided here; feature 016 adds the points and the correct answer to E07.
- E07 is a component shown by the task screen when the task has a submission; there is no separate address. Feature 017 (repeating a task) will decide how the task is opened again.
- `useBlocker` of React Router works only in a data router. `main.tsx` uses `createBrowserRouter` with one route `*` that renders `App`, so the other routes do not change. Tests that render a page with the leave dialog use `createMemoryRouter`. Closing the browser tab is not covered (the browser’s own dialog is not in `docs/`).
- The class and the student come from the session, never from the request; a task of another class is “not found”, not “forbidden” (as in feature 013).
- The warning of feature 013 stays above the form.
- The answer field limit of 100 characters is also the limit for an option; the options of feature 010 (species and group names, month numbers) are shorter.
